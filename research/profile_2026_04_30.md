### H1 — XC grid-setup memoization (NEW lever)

**Observation.** `Exchange-correlation grid setup` is **154 ms** = 33% of "Initialize SCF" and 8% of total wall. It runs **once** per call to `g2g_new_grid` — for static-geometry single-point this never needs to recompute. For MD/Ehrenfest, atom positions move, so weights change. Currently no caching across SCF cycles.

**Plan.** Add a fingerprint hash over (atom positions, basis radii, grid params). Inside `regenerate_partition.cpp` (or wherever `g2g_new_grid` lands), short-circuit when fingerprint matches the prior call. Becke weights and per-group function lists are pure functions of geometry.

**Risk.** Low; pure cache. Need to invalidate on geometry change.

**Why this isn't already done.** Single-point flows call grid setup once — no re-call to memoize. But MD calls it ~once/step; if the hash hits often (e.g. constrained-geometry restarts), this trickles in. For single-point, the lever is the **154ms one-time** itself, not memoization — i.e. profile *inside* `Exchange-correlation grid setup` to find what's slow (Becke weights? cube assignment?). Expected sub-150ms breakdown:

- partition build (atoms→prism→cubes/spheres): ?
- assign_functions_as_cube/sphere: ?
- compute_weights kernel launch + readback: ?

This is the highest-ROI immediate next step: **add Timer instrumentation inside `regenerate_partition.cpp` and `compute_weights` host wrapper** so we know which sub-step dominates 154ms.

**Estimated saving.** 60–120ms if a hot sub-step turns out to be a 1-shot CPU loop that can be vectorized or moved to GPU; pure compute_weights kernel time is only 3ms so it's the surrounding partitioning logic that eats time.

### H2 — int3lu ↔ g2g per-iter overlap (research priority #1)

**Observation.** Per-iter critical path is `int3lu (12.9ms CPU) → g2g.solve (20.0ms CPU+GPU)` — strictly sequential. g2g.solve internally has 5ms CPU-idle while waiting for GPU. If int3lu work can run on a separate thread in parallel with g2g's GPU phase, theoretical saving = 12.9 × 25 = **322ms** (~14% wall). Realistic: thread contention drops it to **200–280ms**.

**Plan.** From `research/fortran/overlap_int3lu_g2g.md`: launch `int3lu` on a Fortran ISO_C_BINDING-pthread before `g2g_solve_groups`. Both write to disjoint Fock blocks (Coulomb fit goes to `Fmat_Coul`; XC goes to `Fmat_XC`). Sum at the end. OpenMP nesting must be configured: int3lu uses some threads, g2g.CPU partition uses 15 threads. With 16 CPU cores (Ryzen 5800X3D = 8 cores 16 threads), overlap is constrained.

**Risk.** Medium. (a) DIIS-history must use bit-identical Fock sums each iteration → guaranteed if no atomic-order changes. (b) OpenMP nesting bugs.

**Effort.** Medium-high. Cross-language thread coordination. Documented in research/fortran/.

### H3 — DSYEVD acceleration (10.2ms/iter × 25 = 256ms)

**Observation.** Diagonalization is 14% of iteration time. M=364, real-symmetric. Reference LAPACK is serial; OpenBLAS LAPACK varies by version.

**Plan A (cheap).** Verify which DSYEVD is actually used (ldd resolves; runtime selection could be different). Try `LD_PRELOAD=libopenblas.so` and confirm OpenBLAS's pthreaded LAPACK is engaged. If not, force it.

**Plan B (mixed-prec).** Use SSYEVD for early iters (rho_diff > 1e-3) and DSYEVD only when converging. Per `research/convergence/algorithmic_reduced_precision_diag.md` (40-80ms est).

**Plan C (GPU).** cuSOLVER `cusolverDnDsyevd` at M=364 is borderline — kernel is fast but H↔D copy of Fock+coeffs (~1MB each way, ~50µs at PCIe 4.0) per iter eats budget. **Net win is unclear without measurement** — recommend prototyping before committing.

**Risk.** Medium for B/C (FP order changes; DIIS history is 30 deep on float32 → tight tolerance). Cheap for A.

---

### H4 — Per-group GPU launch coalescing

**Observation.** `cudaLaunchKernel` shows 6,112 calls / 48ms host time. With 44 GPU groups × 25 iters × ~5 kernels/group = ~5,500 launches just inside iteration. Per-launch overhead ~8µs avg = ~44ms total (matches). Many groups have nearly identical configurations differing only by group index.

**Plan.** Two avenues:
1. **CUDA Graphs**: capture once per partition lifetime (geometry static), replay each iteration. Low effort. Research lists this as LOW impact (`optimize_cuda_graphs.md`) — but fresh data shows 44ms launch overhead, which is reachable.
2. **Batched kernel**: pack several groups into one kernel grid (already partially done via grid+stream sharding rejected for fgm=-1 reasons). Higher effort; lower upside.

**Risk.** Low for graphs (orthogonal to numerics), pending the per-iter rebalancer's group reordering — which would invalidate the captured graph. Need to disable rebalance after some warmup iter.

---

### H5 — Density kernel memory traffic

**Observation.** Density is 260ms = memory-bound. ptxas shows 48 regs, no spills, so it's not register-limited. From roofline (research): operating at 52-69% of realistic ceiling.

**Plan.** Two angles:
- **L1/shared-memory tile of RMM block**: density reads RMM via texture; if sub-blocks reused across point-tiles, shmem could halve global traffic. Already partially warp-shuffle optimized.
- **vec4 → vec2 packing of function values**: function arrays are vec4 floats; if local fits, repacking might increase L1 hit rate. Speculative.

**Risk.** Medium. FP-order preserved if reductions kept identical. Has been worked on extensively.

**Why not higher.** Existing research already lists density-as-GEMM and the roofline ceiling is in sight. Hard yards.
