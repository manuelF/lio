✦ Here is the comprehensive plan for the upcoming optimizations, ranked by their projected impact on GPU utilization and performance.


  1. GPU-side RMM Gather/Scatter (In Progress)
   * Description: Move the preparation of the group-local density matrix and the accumulation of results (RMM update) from the CPU to CUDA kernels.
   * Assessment:
       * Impact: High. It eliminates the most significant bottleneck: the small, synchronous H2D/D2H transfers and CPU-side loops that occur for every point group.
       * Risk: Medium (Numerical correctness depends on matching the Fortran packed indexing exactly).
       * Status: Implementing fix for indexing logic to restore mathematical convergence.


  2. Double/Triple Buffering Pipeline
   * Description: Use the CudaWorkspace to hold data for multiple groups simultaneously. While the GPU is executing kernels for Group $N$, the next stream will be performing
     Transposes and RMM Gather for Group $N+1$.
   * Assessment:
       * Impact: High. This is the primary way to "hide" preparation latency and keep the GPU execution units at 100% duty cycle.
       * Difficulty: Medium. Requires refactoring the Partition::solve loop to submit work for the "next" group before synchronizing on the "current" one.


  3. Kernel Fusion: Density + Accumulate
   * Description: Combine the gpu_compute_density (which calculates the density at each point) and gpu_accumulate_point (which weights and sums them for energy/forces) into
     a single kernel.
   * Assessment:
       * Impact: Medium-High. Currently, partial_densities_gpu is written to global memory and immediately read back. Fusion keeps this data in registers/shared memory,
         significantly reducing memory bandwidth pressure.
       * Difficulty: High. Increases register pressure; requires careful tuning to maintain occupancy.


  4. Asynchronous Energy/Force Reductions
   * Description: Use pinned host memory (cudaHostAlloc) for the energy and force results. Use cudaMemcpyAsync to transfer these results back to the CPU without blocking the
     execution of the next group.
   * Assessment:
       * Impact: Medium. Reduces the "tail" latency at the end of each group's execution where the CPU waits for the final scalar values.
       * Risk: Low. Very standard optimization.


  5. Task Batching for Small Groups
   * Description: For systems with many small "cubes" (low point counts), launch a single kernel that processes multiple groups at once (using an offset array) instead of
     many individual launches.
   * Assessment:
       * Impact: High (for large systems/small grids). Launch overhead becomes dominant when kernels run for only a few microseconds.
       * Difficulty: High. Requires significant changes to how PointGroup data is laid out in memory.

  Immediate Next Steps:
   1. Correct RMM Indexing: Ensure the GPU Gather/Scatter produces bit-identical results to the original CPU implementation to pass the agua and fosfato tests.
   2. Pipeline Implementation: Structural change to Partition::solve to implement the buffering mentioned in point #2.
   3. Validation: Verify speedup using the internal LIO timers.
